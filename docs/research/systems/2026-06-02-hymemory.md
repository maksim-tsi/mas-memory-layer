## 2. Architecture Summary

Hy-Memory presents itself as a layered long-term memory system for agents. The
official site describes a six-layer memory structure:

- L1 raw traces;
- L2 atomic facts;
- L3 identity profile;
- L4 session summary;
- L5 mental model;
- L6 prospective intention.

The architecture is paired with two processing paths:

- **System1**, an online fast path that writes L1-L4 during interaction;
- **System2**, a slower background path that condenses higher-order L5-L6
  memory from System1 material.

The most distinctive architectural claim is memory evolution. Hy-Memory argues
that memory should not merely accumulate records. Instead, older statements are
extracted, merged, updated, and linked so the agent retains a cleaner and more
current model of the user.

## 3. Implemented Technology

The OpenClaw integration guide documents a Python subprocess-based plugin
started by OpenClaw. The example configuration uses:

- Hunyuan 3.0 Preview through OpenRouter as the LLM;
- SiliconFlow BAAI/bge-m3 as the embedding model;
- Chroma as the vector store;
- `userId` as the primary user-memory discriminator;
- `autoRecall` and `autoCapture` toggles;
- `topK` for recall.

The guide states that Hy-Memory currently requires explicit installation with
OpenClaw's unsafe plugin flag because it starts a Python subprocess. This is a
deployment and trust-boundary signal, not necessarily a weakness, but it should
be recorded because it differs from purely in-process library integration.

Not enough information was identified in open sources to determine Hy-Memory's
exact internal storage schema, indexing strategy, lifecycle worker
implementation, authorization model, or runtime error contract.

## 4. Memory Lifecycle

### Capture

The official architecture says System1 writes every conversation into L1 raw
traces and may immediately extract L2 atomic facts, L3 identity profile, and an
L4 session summary.

### Filtering

The site mentions an attention gate that decides whether material is worth
processing. Not enough information was identified in open sources to determine
the gate's scoring formula, whether it is heuristic or model-based, how it
handles false positives, or whether it exposes explanations.

### Condensation

Hy-Memory's condensation path is documented as:

- raw dialogue and behavior become L2 retrievable facts;
- stable preferences and traits become L3 identity profile;
- sessions become L4 summaries;
- background System2 condenses L5 mental models and L6 prospective intentions.

The exact prompts, schemas, merge rules, or profile-update policy were not
identified in open sources.

### Retrieval

The OpenClaw guide documents `topK`, `autoRecall`, embeddings, and Chroma as
the example vector store. The official site also emphasizes supersedes chains:
when any memory in an evolution chain is hit, the whole causal chain can be
expanded.

Not enough information was identified in open sources to determine how vector
similarity, chain expansion, profile matching, and layer selection are fused in
ranking.

### Update, Deletion, And Supersession

The strongest lifetime-management claim is the `supersedes` chain. The site
shows a user attitude evolving across several memories and claims that
supersedes pointers are created at write time. This is highly relevant because
it addresses a known vector-retrieval weakness: semantically distant but
causally relevant intermediate memories may not be retrieved by embedding
similarity alone.

Not enough information was identified in open sources to determine deletion
semantics, retention policy, user-editing behavior, or whether old facts are
hidden, invalidated, archived, or simply linked as history.

## 5. Decision-Making Model

Hy-Memory appears to use a fixed layered pipeline with online and background
processing paths. The system is not documented as a learned RL memory manager.
It is also not documented as a fully agent-decided memory tool interface in the
AgeMem sense. Its public framing is closer to a professional memory kernel with
explicit layer semantics and evolutionary chain construction.

## 6. Benchmark Evidence

The official site claims strong results on LongMemEval and PersonaMem:

- LongMemEval total score of 85.20%;
- PersonaMem total score of 76.91%;
- per-category wins against mem0 and Graphiti in the presented tables;
- faster write-processing time than Graphiti in the reported setup.

These are benchmark claims from the project page. They were not reproduced in
this work. The site discloses a Memory/Answer model, judge model, evaluation
time window, data sources, and compared systems, but open source scripts for
reproduction were not identified during this pass.

## 7. Strengths

- Clear six-layer conceptual architecture.
- Strong user-profile and preference-evolution framing.
- Explicit distinction between online fast processing and background slow
  consolidation.
- Supersedes-chain framing directly addresses temporal evolution and causal
  context loss.
- OpenClaw integration appears practical and configurable.
- Public benchmark claims are directly targeted at memory benchmarks.

## 8. Gaps And Unknowns

- No Hy-Memory code-level implementation source was identified.
- Filtering algorithm and attention-gate details are not public in the sources
  inspected.
- Retrieval fusion and chain-expansion ranking are not specified.
- Retention, deletion, security, multi-tenant isolation, and audit logging are
  not sufficiently documented.
- MCP, REST, and structured public error contracts were not identified.
- The benchmark methodology is more disclosed than many product pages, but not
  independently reproduced here.

## 9. Relevance To YAAM Requirements

Hy-Memory appears relevant to:

- `YAAM-REQ-0006` and `YAAM-REQ-0007`, because its layered memories include
  conversation-derived facts and cross-session recall;
- `YAAM-REQ-0009`, because supersedes chains imply source continuity, although
  full provenance response shapes are not documented;
- `YAAM-REQ-0029`, because supersession/evolution is a central product claim.

Fit is unclear or weak for:

- `YAAM-REQ-0001` through `YAAM-REQ-0004`, because distinct API Wall, REST v2,
  and MCP-style public contracts were not identified;
- `YAAM-REQ-0010` through `YAAM-REQ-0013`, because security, scoping,
  read-only resources, and write allowlisting are not sufficiently documented;
- `YAAM-REQ-0014` through `YAAM-REQ-0018`, because Phoenix-style tracing,
  Evidence Table generation, CIAR explanation, and partial-result contracts are
  not documented;
- domain-pack and benchmark-leakage requirements such as `YAAM-REQ-0036`
  through `YAAM-REQ-0039`.

## 10. Research Interpretation

Hy-Memory is a strong competitor at the level of layered cognitive memory,
profile evolution, and public benchmark positioning. Its design is closest to
YAAM in the intuition that raw memory must be processed into increasingly
structured and durable forms. Its public evidence is weaker than YAAM's on
service contracts, scoped auditability, and interface governance, but stronger
on product polish and published memory-benchmark claims.
