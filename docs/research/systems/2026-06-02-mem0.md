Mem0 should be treated as both an open-source memory library/server and a
managed platform. Public claims differ by mode; hosted platform governance
should not be assumed for minimal OSS library use.

## 2. Architecture Summary

Mem0 positions itself as a universal memory layer for AI agents. Its public
materials describe:

- persistent contextual memory;
- multi-level memory across user, session, and agent state;
- vector-based memory storage;
- LLM-based extraction and processing;
- optional graph memory for relationships;
- rerankers and async-by-default behavior in recent releases;
- managed platform, self-hosted server, and lightweight library modes.

Compared with Graphiti, Mem0 appears more productized as a general-purpose
memory layer and less strictly centered on temporal graph semantics. Compared
with TencentDB-Agent-Memory, it is less local-artifact-oriented and more SDK/API
or platform oriented.

## 3. Implemented Technology

The repository and documentation identify:

- Python and TypeScript SDKs;
- CLI;
- managed cloud platform;
- self-hosted server with dashboard and auth;
- default LLM usage, with `gpt-5-mini` named in the README at the time of
  inspection;
- default embedding model `text-embedding-3-small`;
- support for vector stores and rerankers;
- optional graph memory with Neo4j, Memgraph, Neptune, Kuzu, or Apache AGE;
- graph memory that mirrors entities and relationships alongside vector memory;
- integrations with LangChain, CrewAI, Vercel AI SDK, browser extension, and
  agent skills;
- MCP documentation in the platform docs navigation.

The graph-memory documentation states that Mem0 extracts entities,
relationships, and timestamps, stores embeddings in a vector database, and
mirrors relationships in a graph backend. At search time, graph memory runs in
parallel and adds related entities in a `relations` array; it does not reorder
vector hits automatically.

## 4. Memory Lifecycle

### Capture

Mem0 exposes `memory.add` for conversations/messages and `memory.search` for
retrieval. The basic pattern is:

1. retrieve relevant memories for a message;
2. inject them into the system prompt or context;
3. generate a response;
4. add the updated conversation to memory.

### Filtering

Mem0 documentation describes LLM extraction of important information from
conversations. The paper describes dynamic extraction, consolidation, and
retrieval of salient information. The exact salience criteria, update policy,
and filtering prompts are not fully specified in the sources inspected.

Not enough information was identified in open sources to determine the complete
production filtering algorithm used by the current managed platform.

### Condensation

Condensation is performed through LLM extraction and memory processing. In
graph memory mode, Mem0 also extracts entities, relationships, and timestamps.
The paper describes consolidation of salient information from ongoing
conversations.

Mem0 does not present a fixed L0-L3 or L1-L6 hierarchy like Tencent systems;
its public layer model is more about user/session/agent memory and vector/graph
storage.

### Retrieval

Retrieval is primarily vector search, with optional reranking and graph-related
context. Enhanced search can include hybrid keyword/entity behavior depending
on configuration. Graph memory augments results with related relations but does
not automatically reorder vector hits according to the graph-memory
documentation.

### Update, Deletion, And Lifetime Management

The README and docs mention add, search, update, and delete workflows. The
paper describes extraction, consolidation, retrieval, and graph memory.

Not enough information was identified in open sources to determine exact memory
decay, TTL, supersession, legal retention, profile overwrite, or conflict
resolution behavior in the current platform. The managed platform advertises
audit logs and workspace governance, but detailed lifetime policy mechanisms
were not fully identified in the inspected sources.

## 5. Decision-Making Model

Mem0 is best characterized as a production memory service/library with LLM
extraction and optional graph augmentation. It appears to use extraction and
update pipelines rather than a learned RL policy. It does not expose unified
STM/LTM actions as part of the base agent policy in the AgeMem sense.

## 6. Benchmark Evidence

The repository claims:

- 91.6 on LoCoMo;
- 94.8 on LongMemEval;
- 64.1 on BEAM at 1M tokens.

The arXiv paper claims:

- 26% relative improvement in LLM-as-judge metric over OpenAI memory;
- graph memory adds about 2% over base configuration;
- p95 latency reduction of 91%;
- more than 90% token-cost savings compared with full-context methods.

These are benchmark and paper claims. They were not reproduced in this work.

## 7. Strengths

- Strong ecosystem adoption and developer ergonomics.
- Multiple deployment modes: library, self-hosted server, cloud platform.
- Clear SDK/CLI/API path for rapid integration.
- Optional graph memory broadens beyond vector search.
- Managed platform advertises audit logs and workspace governance.
- Broad integration surface across popular agent frameworks.
- Strong public benchmark claims and a citable paper.

## 8. Gaps And Unknowns

- Current production filtering and consolidation internals are not fully
  specified.
- Graph memory augments relations but is documented as not automatically
  reordering vector hits.
- Exact temporal invalidation/supersession semantics are less explicit than
  Graphiti.
- Structured Evidence Table, CIAR explanation, benchmark leakage guards, and
  YAAM-style trace correlation were not identified.
- Hosted platform governance should not be assumed for OSS library mode.

## 9. Relevance To YAAM Requirements

Mem0 appears relevant to:

- `YAAM-REQ-0002` and `YAAM-REQ-0003`, because memory search and context
  injection are core product behaviors;
- `YAAM-REQ-0005` through `YAAM-REQ-0008`, at a general memory-operation level,
  although Mem0 does not map cleanly to YAAM's L2/L3/L4 tiers;
- `YAAM-REQ-0010`, because user/session/agent scoping is documented;
- `YAAM-REQ-0034`, due to published latency and token-efficiency claims.

Fit is partial or unclear for:

- `YAAM-REQ-0001` through `YAAM-REQ-0004`, because YAAM's distinct API Wall,
  REST v2, and MCP roles are not mirrored;
- `YAAM-REQ-0009`, because provenance is not as central in public docs as in
  Graphiti or YAAM;
- `YAAM-REQ-0011` through `YAAM-REQ-0018`, because read-only resources,
  write allowlists, redaction, Evidence Table, CIAR explanation, and
  partial-result contracts are not clearly identified;
- `YAAM-REQ-0029`, because contradiction/supersession is not as explicit as
  Graphiti temporal invalidation or Hy-Memory supersedes chains;
- `YAAM-REQ-0036` through `YAAM-REQ-0039`, because benchmark leakage, curation,
  and trace-correlation contracts are not identified.

## 10. Research Interpretation

Mem0 is a strong production and ecosystem competitor. It is probably the
easiest system in this set to adopt quickly in general-purpose applications.
Relative to YAAM, it appears stronger in adoption, packaging, and managed
memory convenience. YAAM is more explicit in research-facing governance,
provenance contracts, CIAR/Evidence Table explanation, benchmark isolation, and
multi-interface service design.
