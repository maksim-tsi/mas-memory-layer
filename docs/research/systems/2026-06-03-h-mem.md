## 2. Architecture Summary

H-Mem proposes a hybrid memory mechanism for long-term agent-memory question
answering. The system is organized around two stages:

- **offline indexing**, which builds a hybrid temporal-semantic tree and
  entity-centered knowledge graph;
- **online retrieval**, which decomposes a query into sub-queries, plans memory
  scope, searches graph and tree structures, ranks evidence, and synthesizes an
  answer.

The central idea is not merely "use a tree and a graph." The paper argues that
long-term memory requires two complementary structures:

- a **temporal-semantic tree** to model memory evolution from short-term events
  into longer-term summaries;
- a **knowledge graph** to support entity-centered retrieval and multi-hop
  reasoning across memory fragments.

This makes H-Mem closer to an indexing and retrieval mechanism than to a full
production memory service. It focuses on how memory should be organized and
retrieved for QA, not on customer-facing governance contracts.

## 3. Offline Indexing

### Tree Construction

H-Mem builds a multi-level temporal-semantic tree. Leaf nodes contain extracted
memory events from raw memory fragments. Upper-level nodes contain summaries of
lower-level events or summaries.

The paper's default temporal levels are day, week, month, and year. A new
memory event is assigned to a temporal window. Within that window, it is
semantically compared against candidate nodes. If similarity exceeds the level
threshold, the event joins a candidate cluster and the parent summary is
updated. Otherwise, a new parent node is created.

The result is a hierarchy in which fine-grained recent events can progressively
consolidate into longer-term summaries. This is the paper's main memory
evolution mechanism.

### Graph Construction

H-Mem also constructs an entity graph. It extracts entities and relations from
memory fragments, normalizes entity types, resolves entity aliases, inserts
relations, and links entities back to original memory fragments.

The paper reports:

- entity extraction through LLM prompts;
- fallback to spaCy NER when LLM extraction fails or returns no valid entities;
- entity types such as person, organization, location, event, product, work,
  date, time, and other;
- exact match, token overlap, and fuzzy matching for entity resolution;
- provenance links from entities and relations back to original fragments;
- entity profiles for salient entities.

Not enough information was identified to determine whether the implementation
exposes a public graph schema, migration mechanism, deletion protocol, or
auditor-facing graph contract.

## 4. Online Retrieval

H-Mem retrieval has three stages.

### Retrieval Planning

Given a query, H-Mem decomposes it into sub-queries with dependency relations.
For each sub-query, an LLM predicts a memory scope:

- `Short`: moment-specific evidence, recent events, concrete actions;
- `Long`: stable memory, preferences, relationships, recurring facts;
- `Mixed`: both fine-grained and higher-level summaries.

The planner also infers explicit temporal hints, such as dates or relative time
cues, when present.

### Evidence Retrieval

H-Mem first searches the graph. It extracts entities from the sub-query, finds
seed entities through lexical and vector search, and expands over the graph to
collect related entities. It then maps graph-linked entities to memory
fragments and tree events.

The tree is searched bottom-up. Retrieval scope determines which levels are
eligible:

- `Short` uses original fragments and leaf events;
- `Long` uses events and summaries;
- `Mixed` uses original fragments, events, and summaries.

### Evidence Ranking

H-Mem ranks evidence using three signals:

- semantic similarity between query and evidence;
- temporal relevance from temporal overlap and temporal distance;
- memory robustness, inspired by the Ebbinghaus forgetting curve and reinforced
  by repeated consolidation or mentions.

This is one of the most relevant H-Mem ideas for YAAM. It separates retrieval
utility from mere vector similarity and introduces a weak temporal/robustness
prior. The paper states that robustness is not intended to dominate semantic or
temporal relevance.

## 5. Filtering, Condensation, And Lifetime Management

H-Mem's filtering is mostly embedded in indexing and retrieval:

- memory events are extracted from raw fragments;
- semantically similar events within temporal windows are consolidated;
- query-time planning selects short, long, or mixed memory scope;
- retrieval uses graph expansion, tree search, deduplication, and reranking.

Condensation is central. Upper tree levels store summaries over longer time
windows, and entity profiles store persistent plus recent entity-centered
information.

Lifetime management is present as memory evolution, not as a full governance
lifecycle:

- memory evolves from events to summaries;
- repeated mentions reinforce memory robustness;
- temporal alignment affects retrieval relevance;
- missing-information queries can trigger targeted second-pass retrieval.

However, the paper does not establish customer-grade retention, deletion,
editing, legal hold, scoped erasure, or audit semantics. The limitations
section explicitly notes privacy risks and says practical deployments should
include user consent, editing/deletion mechanisms, access control, and
transparent auditing.

## 6. Technology And Experimental Configuration

The paper reports the following experimental configuration:

- backbone LLMs: GPT-4o-mini and GPT-4.1-mini;
- default semantic retrieval and reranking: Qwen3-Embedding-4B and
  Qwen3-Reranker-4B;
- lighter retrieval configuration: Qwen3-Embedding-0.6B and
  Qwen3-Reranker-0.6B;
- hardware: Linux server with Intel Xeon CPU, 1024 GB memory, and eight NVIDIA
  RTX A5000 GPUs.

This is strong experimental disclosure for a paper, but it also indicates a
potentially heavy offline indexing profile. The paper itself reports that
H-Mem has higher indexing token cost and storage than many simpler baselines,
because it constructs events, summaries, entities, relations, entity profiles,
and both tree and graph structures.

## 7. Benchmark Evidence

The paper evaluates H-Mem on:

- LoCoMo;
- LongMemEvalS;
- REALTALK.

It reports stronger overall QA performance than MemoryOS, Mem0, MemTree,
MemOS, Zep, and EverMemOS, with particular gains on multi-hop and temporal
questions. The ablation study reports that removing the tree causes the largest
performance drop, followed by removing the graph. Removing long-term memory,
memory robustness, missing-information queries, or entity profiles also
reduces performance.

These are paper claims, not reproduced YAAM evidence. The results should not be
used to claim H-Mem superiority in YAAM's deployment context without a separate
benchmark reproduction protocol.

## 8. Strengths

- Strongly specified hybrid index concept: temporal-semantic tree plus entity
  graph.
- Directly targets long-term memory evolution rather than append-only storage.
- Explicit retrieval planning and query decomposition.
- Evidence ranking combines semantic, temporal, and robustness signals.
- Graph expansion supports multi-hop reasoning.
- Tree summaries support retrieval over both fine-grained and persistent
  memory.
- Ablation studies identify which components drive performance.
- Limitations section acknowledges privacy, deletion, access-control, and audit
  needs.

## 9. Gaps And Unknowns

- No public implementation repository was identified in this pass.
- No production API, REST, MCP, or SDK contract was identified.
- Not enough information was identified to determine production schema,
  migration, retention, or deletion semantics.
- Not enough information was identified to determine tenant, project, session,
  run, or benchmark isolation semantics.
- Not enough information was identified to determine how source provenance is
  exposed to external consumers, even though provenance links are described
  internally.
- The system relies on LLM extraction and retrieval planning, making it
  vulnerable to extraction error, query decomposition error, and scope
  prediction error.
- Offline indexing may become expensive for very long or frequently updated
  conversations.
- Benchmarks were not reproduced locally and are not directly comparable to
  YAAM without a controlled protocol.

## 10. H-Mem Versus Hy-Memory

H-Mem and Tencent Hunyuan Hy-Memory are related but not equivalent.

| Dimension | H-Mem | Hy-Memory |
| --- | --- | --- |
| Evidence source | Research paper | Product/official documentation |
| Core concept | Temporal-semantic tree plus entity graph | Six-layer memory stack with System1/System2 workflow |
| Evolution model | Temporal-window consolidation into tree summaries | Memory evolution and supersedes-chain framing |
| Retrieval model | Agentic query decomposition, graph expansion, tree search, scoring | Multi-layer recall and supersedes-chain expansion; exact ranking insufficiently public |
| Implementation evidence | Paper configuration and experiments; no repo identified | OpenClaw plugin configuration; no Hy-Memory internals repo identified |
| Governance evidence | Limitations mention need for consent, deletion, access control, auditing | Public documentation did not expose full governance semantics |

Hy-Memory is broader as a product concept and closer to a layered memory
platform. H-Mem is more precise as an algorithmic indexing/retrieval proposal.
H-Mem gives stronger detail on tree construction, graph extraction, retrieval
planning, and evidence scoring. Hy-Memory gives stronger public product signal
and a clearer cognitive layer narrative. Neither public source establishes
YAAM-equivalent public contracts, scoped access, Evidence Table semantics,
Phoenix-style traceability, or benchmark leakage controls.

## 12. YAAM Fit Assessment

H-Mem is a valuable research reference, but not a system YAAM should import
wholesale.

YAAM already has natural analogues:

- L3 uses Qdrant and Neo4j, matching H-Mem's need for semantic and graph
  retrieval.
- L4 distillation already stores generalized knowledge documents.
- CIAR and lifetime decision classes already expose policy-level provenance.
- Phoenix tracing already supports live evidence classification.

The main H-Mem opportunity is retrieval evaluation and ranking, not a new
storage stack. YAAM can learn from H-Mem by testing whether L3 retrieval should
combine:

- Qdrant similarity;
- Neo4j entity/relationship support;
- temporal alignment from episode timestamps and validity windows;
- CIAR/lifetime evidence metadata as a governance-aware robustness signal;
- evidence-gap detection for targeted follow-up retrieval.

The main risks of adopting H-Mem literally are:

- a new temporal tree schema would increase storage and migration complexity;
- tree maintenance may duplicate YAAM's existing L2-L3-L4 lifecycle engines;
- query-planner LLM calls in the hot path could raise latency and provider
  variance;
- an H-Mem-style index may optimize QA benchmarks while weakening YAAM's
  governance-first interface posture if adopted without careful boundaries.

## 13. Recommendation

Do not implement a full H-Mem temporal-semantic tree in YAAM now.

The recommended future work is a small RFC, not immediate implementation:

> Evaluate an H-Mem-inspired L3 retrieval scoring experiment that uses existing
> YAAM data only: Qdrant similarity, Neo4j entity links, episode timestamps,
> CIAR/lifetime provenance, and Phoenix-observed evidence chains. The experiment
> should compare current L3 retrieval with a hybrid scorer and report memory
> precision, recall, temporal correctness, provenance completeness, and leakage
> guard behavior.

This preserves YAAM's architecture while testing the H-Mem idea where it is
most likely to add value.
